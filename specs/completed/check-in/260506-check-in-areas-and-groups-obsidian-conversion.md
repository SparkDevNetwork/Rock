# Check-in Areas and Groups: WebForms to Obsidian Conversion

## Summary

The legacy `CheckinAreas` WebForms block is being rewritten as the Obsidian `CheckInAreasAndGroups` block. The deliverable targets the Figma redesign (campus and area slicer, split-pane editor, redesigned item states, 5-level nesting, reorganized Area / Group editors), not a one-for-one port of the legacy UI. Side-by-side conversion: the legacy block stays in place until the new block is confirmed working end-to-end. The legacy `BlockTypeGuid` is preserved untouched.

## Motivation

Two drivers:

1. **WebForms phase-out.** Rock is migrating off WebForms; this block is part of that broader effort.
2. **New design.** The Figma redesign introduces a slicer (campus context plus an Areas dropdown), a split-pane editor with Area and Group right-pane variants, redesigned item states, structured 5-level nesting, and named-location filtering by selected campus. A direct port of the legacy UI would be wasted work, since most of the legacy chrome does not survive the redesign.

Using the legacy block as a behavior-and-data-flow reference (entity model, save semantics, business rules) but not as a UI template is a deliberate choice that shapes the rest of this spec.

- Pre-selection navigation guard for unsaved editor changes. New `:beforeSelect?: (node) => boolean | Promise<boolean>` prop on `<SortableTree>` intercepts row clicks before the selection commits and before auto-expand-on-collapsed fires; returning or resolving to `false` suppresses the selection so the previous one stays in place (no flicker from a watcher-driven revert). Provide / inject pair in `utils.partial.ts` wires the block-level guard to consumers: `provideNavigationGuard` / `useNavigationGuard` for the predicate itself, and `provideUpdateEditorIsDirty` / `useUpdateEditorIsDirty` so the active editor pushes its dirty state up (replacing an earlier v-model:isDirty / v-model:errorMessage cascade). Confirms via `confirm()` for now; switchable to Rock's confirm dialog later. On confirmed discard from a placeholder node, the guard also removes the placeholder from the tree so it doesn't linger as orphan state. The editor's `onBeforeUnmount` calls `updateEditorIsDirty(false)` so a navigated-away-and-back panel doesn't leak its previous dirty state.

- Dirty tracking is interaction-based, not snapshot-based. Both editors track a `wasformTouched` ref instead of diffing a JSON snapshot of `buildBag()`. `onMounted` attaches `input` / `change` listeners to the pane body element (`bodyEl`); those DOM events fire only on genuine user interaction, while Vue's programmatic value sets do not, so the `<AttributeValuesContainer>`'s async `<RockField>` children emitting `update:modelValue` on mount (a `DropDownList` falling back to its first option when the persisted value isn't in its list, etc.) no longer trip dirty. Controls whose changes flow through Vue emits rather than DOM events (the group editor's Named Locations grids, the area editor's two `LabelGrid`s) bind explicit `@update:*` handlers that call `markFormTouched()`. `isDirty` is `!entity ? false : !entity.idKey || wasFormTouched.value` (an unsaved placeholder is always dirty). `seedFromBag` resets `userTouched = false`; `onBeforeUnmount` removes the listeners. Replaces the prior JSON-snapshot approach, whose snapshot drifted after the AVC's mount-time emits and latched `isDirty` true forever (and the 500ms stabilization-window workaround that briefly papered over it). Accepted trade-off: typing a value and then restoring it leaves `wasFormTouched` true, so navigate-away still prompts; rare and acceptable.

- Placeholder draggability suppressed. New `:isNodeDraggable?: (node) => boolean` prop on `<SortableTree>`, forwarded recursively to child rows and AND'd with the local sibling check so single-child rows and consumer-rejected rows both end up non-draggable. ListPane returns `!isPlaceholderKey(node.idKey ?? "")` so unsaved sentinel-key rows can't be dragged; the server's `ReorderArea` / `ReorderGroup` resolve the `0` sentinel to null and respond "Area not found" / "Group not found," so prevention is at the source.

- Placeholder insertion respects tree sort order. New areas insert at the parent's `firstGroupIndex` (or end if no groups exist) rather than appending unconditionally. Matches the server tree builder's areas-first / groups-after ordering so the placeholder lives among its siblings as the user expects.

- Save-success notification. Top of `.ag-pane-body` in the detail pane uses `<NotificationBox v-if="saveSuccessMessage" :alertType="AlertType.Success">`. Sticks until the next selection or save event clears it (no auto-dismiss timer). Mirrors legacy `nbSaveSuccess` placement.

- Inline validation rendering. `<RockForm hideErrors @visibleValidationChanged="...">` suppresses RockForm's default top-of-form error stack; the editor renders `<RockValidation :errors="formErrors" />` inside the body so validation errors scroll with the rest of the content rather than visually competing with the panel title.

AreaEditor scrolls when `saveSuccessMessage`, `errorMessage`, or `formErrors.length` transitions from empty to non-empty; ListPane scrolls when its `errorMessage` (reorder error) transitions. The detail pane also scrolls to top whenever the selected `idKey` changes.

- Reorder error surfaced in the list-pane body. ListPane carries an `errorMessage: string` prop; the parent's `reorderErrorMessage` binds to it and is cleared at the top of `onReorder`. Renders inside `.ag-pane-body` (above the tree) rather than at the panel level so the alert sits within the pane's padding rhythm. Not dismissible: the next reorder attempt clears it, matching how the area editor handles its own save errors.

- `SaveArea` circular-FK fix. `DefaultGroupRoleId` is now set by-value after the first `SaveChanges`, not via the nav property before save. Setting it as the nav property tried to insert the role and the GroupType in a single graph; each FK pointed at the other's pending Id and EF surfaced "Unable to determine a valid ordering for dependent operations." - Group editor (Null / Check-in variant) end-to-end. `GroupDetailBag` (`IdKey`, `Name`, `IsActive`, `IsSpecialNeeds`, `ParentAreaName`) and `SaveGroupRequestBag` (`Group`, `ParentIdKey`, `ParentNodeType`). Create branch resolves the parent (Area or Group) via cache, derives `GroupTypeId` / `ParentGroupId`, and computes the next `Order` from a sibling-MAX query that matches `ReorderGroup`'s "root group under area X" predicate (`g.GroupTypeId == X.Id && ( g.ParentGroupId == null || g.ParentGroup.GroupTypeId != X.Id )`) so a placeholder's Order doesn't collide with a cross-area-parent root sibling. Client side: `groupEditor.partial.obs` mirrors `areaEditor.partial.obs`'s skeleton (RockForm + `hideErrors`, save-success / error / RockValidation banners, ContentSectionContainer, dirty-by-`wasFormTouched` via `useUpdateEditorIsDirty`, footer Save + Cancel/Delete). DetailPane routes to `<GroupEditor v-else-if="isGroupSelected">` and adds `loadedGroup` / `loadGroupDetail` / `onGroupSave` / `onGroupDelete` mirroring the area side; placeholder deletes short-circuit the server call. - Projection helpers, two flavors. `ToAreaDetailBag( GroupTypeCache area )` is cache-only (`GroupTypeCache.Attributes` is auto-hydrated, so `GetAreaDetail` reads from cache and `SaveArea` re-fetches via `GroupTypeCache.Get( area.Id )` after `SaveChanges` invalidates the entry). `ToGroupDetailBag( Model.Group group )` is entity-only and requires the caller to have called `LoadAttributes` first: `GetGroupDetail` loads via `GroupService` + `LoadAttributes`, and `SaveGroup` passes the tracked entity directly (it already calls `LoadAttributes` before staging values). This split exists because `GroupCache.Attributes` resolves the inherit chain at hydration time and never re-resolves when an ancestor area's `InheritedGroupTypeId` changes (the standard cache invalidation path only touches the directly-edited entity, not descendants), so reading from the cache would surface a stale filter schema. Re-resolving via `LoadAttributes` on each `GetGroupDetail` walks the chain freshly, matching how the legacy `<Rock:CheckinGroup>` control populated its filter fields on every postback. One DB hit per group selection.

- `SaveArea` flushes downstream `GroupCache` entries when `InheritedGroupTypeId` actually changed. Captures the prior value before assignment, compares to the resolved new value, and on change runs `FlushGroupCachesForAreaInheritedAttributes( area.Id )` (single `SELECT Id FROM [Group] WHERE GroupTypeId = area.Id` plus a per-row `GroupCache.Remove`). ## Planned Change: All-Locations Model for Named Locations

**Status: implemented** (see the matching Done bullet above). This section is retained as the decision record; the model, removals, and edge-case rationale below describe what was built. One refinement landed during implementation: the campus context (the `selectedCampus` Guid as well as `campusRootLocationGuid`) is owned by the block, which runs the single browser-bus subscription and provides both refs down via `provideSelectedCampus` / `provideCampusRootLocationGuid`. An intermediate iteration moved the subscription into `namedLocationsSection` itself; that was reverted to keep campus context centralized at the block so future campus-aware consumers can inject it rather than stand up their own bus lifecycle.

### Why

The campus slicer scopes the Group editor's Main/Overflow location grids to the active campus. The current implementation loads only the active campus's locations and stamps the bag with that campus so the save reconciles safely (no cross-campus data loss). That made the *save* correct, but the *display* still goes out of sync with the slicer: after the admin changes campus and cancels the refresh prompt, the grids keep showing the load-time campus's locations while the slicer reads a different campus (or "All Campuses"). That's confusing ("the slicer says All Campuses but I see Main's rooms / get an error"), and the framework owns the campus context so we can't revert the slicer on cancel. The root cause: we only loaded one campus's locations, so we can't re-filter the display when the slicer moves without a server round-trip.

### The model

Ship **all** of the group's attached locations (every campus), each tagged with its campus, and derive the displayed grids by **filtering client-side** on the active campus. The slicer becomes a pure view filter over already-loaded data.

- Slicer change → re-filter the loaded list client-side. No server round-trip, no refresh prompt, no limbo. The display always matches the slicer.
- Edits live in the full list, so they survive slicer changes (edit Main's rooms, switch to West and back, the Main edits are still there).
- Save sends the full list → a full (unscoped) reconcile. No data loss, because the bag is the complete authoritative set again (as it was pre-per-campus).
- Campus is a display lens, not a permission, so shipping all campuses' locations to a campus-scoped admin is fine (they can already see everything via "All Campuses"). No security concern.

### What this removes (revert these)

- `GroupDetailBag.LocationsCampusIdKey` (the stamp) and its `.d.ts` field; the `ToGroupDetailBag` stamp assignment; the `buildBag` passthrough in `groupEditor.partial.obs`.
- The stamp resolution + scoped reconcile in `SaveGroup` / `TryReconcileGroupLocations` (`scopeCampusId` param) — `TryReconcileGroupLocations` goes back to a full reconcile over all `group.GroupLocations`.
- The `scopeCampusId` param on `TryResolveAttachedLocationId` and the cross-campus reject branch (a full reconcile accepts all campuses, so there's no out-of-scope reject — and thus no mixed-bag edge case).
- The campus filter inside `GetAttachedNamedLocations` (it returns all locations again).
- The `detailRefreshToken` campus-change refresh: `checkInAreasAndGroups.obs` no longer needs to re-fetch the open detail on campus change (the client re-filters). Keep `updateCampusRootLocationGuid` (the picker still scopes to the live campus for *adds*). The `ContextEntityChanged` campus handler shrinks to just updating the picker scope.
- `IsLocationInCampus(location, campusId)` may stay (the picker add path still validates against the live campus via `ResolveNamedLocation`), or revert to the simpler `IsLocationInActiveCampus` — implementer's call.

### What this adds

- **`NamedLocationBag` gains a campus tag** so the client can filter: add `CampusGuid` (Guid?) — or `CampusIdKey` — set in `BuildNamedLocationBag` from `NamedLocationCache.Get(locationId)?.CampusId` → `CampusCache.Get(id)?.Guid`. (Null campus = a location not under any campus root; decide whether such a location shows under "All Campuses" only or always — recommend All-Campuses-only, consistent with the rest.)
- **Client filtering in `namedLocationsSection.partial.obs` (or `groupEditor`)**: the grids bind to computed views of the full `locations` / `overflowLocations` filtered by the active campus (null/All Campuses → show all). The active campus comes from the same context the picker scope uses (inject the campus, or reuse `campusRootLocationGuid`'s source — note we need the campus *id/guid*, not the root location guid, so prefer injecting the campus context directly).
- **Server full reconcile**: `TryReconcileGroupLocations` reconciles the entire bag against all `group.GroupLocations` (delete rows not in the bag, add/update the rest). This is essentially the pre-per-campus reconcile.

### The one fiddly part: reorder write-back

The grids bind to a *filtered* view, but `<ReorderColumn @orderChanged>` reorders within that view. The handler must map the reorder back into the full list, leaving other campuses' entries in place. Options: (a) keep the full list as the source and splice the moved item to its new position relative to `beforeItem` within the full array (both are in the active campus subset, so their relative order in the full list is what changes); or (b) store locations per-campus (a map keyed by campus) and bind the active campus's list directly, flattening to the full list on save — sidesteps the mapping but complicates "All Campuses" (which would show the union). Recommend (a). Either way, `GroupLocation.Order` stays per-campus in practice (check-in consumes locations per-campus), so cross-campus `Order` overlap remains fine.

### Edge cases this resolves

- Slicer/display mismatch after a campus change → gone (display is derived from the slicer).
- "All Campuses still errors" → gone (full reconcile, no scope reject).
- Canceled-refresh limbo → gone (no refresh needed; nothing to cancel).
- All-Campuses partial-bag data loss → gone (the bag is always the full set).

### Verification when done

- Group with locations in 2+ campuses: switch the slicer among campuses and All Campuses — grids re-filter instantly, no round-trip, no prompt.
- Edit Main's locations, switch to West and back — Main edits preserved.
- Save under any slicer setting → all campuses' locations persist correctly; none orphaned.
- Reorder within a campus, save, reload → order preserved for that campus, others unchanged.
- Add via picker (scoped to live campus) → lands in the active campus's filtered grid and the full list.

### Bag architecture

Two layers, separated by what changes in response to client interaction. Modeled on `ConnectionOpportunityNavigation` and `ConnectionTypeNavigation`.

**InitializationBox** (`CheckInAreasAndGroupsInitializationBox : BlockBox`). Shipped once at startup, holds state that does not change as block actions fire. Currently:

- `CheckInTypeName`. Panel title (parent `GroupType` name).
- `AreaItems`. `List<ListItemBag>` of all check-in area descendants under this configuration (flat, includes nested sub-areas), excluding `CHECKIN_FILTER` purpose group types. Drives the Areas dropdown.
- `SelectedAreaPreferenceKey`. Per-configuration preference key, format `SelectedArea_ConfigurationIdKey_{IdKey}`. Client reads / writes via `usePersonPreferences().blockPreferences`.
- Inherited from `BlockBox`: `ErrorMessage`, `NavigationUrls`, `SecurityGrantToken`.

Planned additions to the box:

- Initial `Tree` snapshot so the page renders without an extra round-trip.
- Initial `ShowInactive`, `DisableAutoCollapse` person-preference values.
- `IsTrailblazerMode` (TBD source).

**Segmented bags.** Returned by block actions on demand, scoped to a single concern.

- `TreeBag`. Returned by `GetTree(GetTreeRequestBag)`. Re-fetched on filter changes, on `ShowInactive` toggle, and after structural mutations.
- `AreaDetailBag`. Returned by `GetAreaDetail(areaGuid)`.
- `GroupDetailBag`. Returned by `GetGroupDetail(groupGuid)`.

**Request bags.** Input payloads for block actions. Pattern: `Get[Thing]RequestBag`. Carries filter and override values from the client.

**Campus context** is supplied by the framework, not by us. `<ContextSlicer showCampus>` provides the picker; `[ContextAware( typeof( Campus ) )]` on the C# class plus `RequestContext.GetContextEntity<Campus>()?.Id` on each block action gives server-side access. The client never passes the campus explicitly. The legacy block had no campus filter; the new design uses campus context to hide named locations whose campus is not the selected one.

### Data flow on filter change

The client wires up two re-fetch triggers:

- **Campus change.** `browserBus.subscribe(PageMessages.ContextEntityChanged, ...)` filtered on `EntityType.Campus`.
- **Local filter dropdown.** Vue `watch(...)` on the slicer's `v-model` refs (e.g., the Areas dropdown).

Both build a `Get[Thing]RequestBag`, call `useInvokeBlockAction()`, and write the returned segmented bag into a local `ref`. The C# action reads campus from `RequestContext.GetContextEntity<Campus>()` and the area override from the request bag.

### Layout

- **Panel height.** `target = innerHeight - naturalTop`, where `naturalTop = rect.top + window.scrollY`. Doc-relative top is scroll-invariant by construction (the `+ scrollY` cancels `rect.top`'s scroll dependence), so the result is stable under page scroll without a scroll listener. Works on both layout types: document-scroll (doc taller than viewport) and worksurface (`documentElement.scrollHeight === innerHeight`). Listens only on `window.resize` plus `ResizeObserver(documentElement)`.
- **Compact-layout breakpoint.** At `isSmOrSmaller`, drop the JS height bound and stack the two panes vertically (page-scroll). At `md+`, the bounded split-pane layout applies. `BreakpointObserver` lives at `CheckInAreasAndGroups/breakpointObserver.partial.obs`.
- **Split-pane partials.** `listPane.partial.obs` and `detailPane.partial.obs`. Parent owns `selectedNodeKey` and `hasAnyAreasOrGroups`.
- **Empty-state visibility.** Keyed by parent state. List pane empty when `!hasAnyAreasOrGroups`; detail pane empty when `!selectedNodeKey`. Copy and layout follow `Figma_EmptyStates.png`.
- **Class naming.** `ag-*` for intra-block elements, `check-in-ag-*` for the outer panel container.
- **Styles** live in `_blocks-checkin.scss` (not scoped in the `.obs`), bracketed with `// ======= CHECKIN AREAS AND GROUPS =======` banners matching the existing Schedule Builder section.
- **`<ExperienceModePicker />`** mounts in the panel's `#headerActions` slot. Custom blocks do not have `showExperienceMode` on `Panel`; only `<DetailBlock>` does.

### Tree rendering and componentization

The recursive tree renderer was lifted out of the block into a generic, reusable Obsidian control: `<SortableTree>` at [Rock.JavaScript.Obsidian/Framework/Controls/sortableTree.obs](../Rock.JavaScript.Obsidian/Framework/Controls/sortableTree.obs), with the recursive node and a drag-auto-scroll composable in `Framework/Controls/Internal/SortableTree/`. Per the Rock-wide convention (see global rule), a component's related files live in a **PascalCase** subdirectory of the same name as the component, so the internal directory is `Internal/SortableTree/`, not `Internal/sortableTree/`. Consumers import from `@Obsidian/Controls/Internal/SortableTree/types.partial`.

Control surface:

- Generic over `<TNode extends SortableTreeNode<TNode>>`. Constraint interface in `Internal/SortableTree/types.partial.ts` declares the minimum shape: `idKey`, `name`, `isActive`, `children`.
- `:groupBy?: (node: TNode) => string | null`. Children are bucketed by the function's return value; each bucket gets its own drag-service id (one drag source per group key, in the order each key first appears among children). Reorder is structurally constrained to same-key siblings.
- `:actions: ISortableTreeAction[]`. Each action declares an icon, a label, a handler, and an optional `isVisible` predicate. Caller does not write slot markup for actions.
- `:dragIconCssClass`, `:defaultIconCssClass` props. Default to `ti-grip-vertical` and `ti-circle-dot` respectively.
- `#title` slot. Default `<p>{{ node.name }}</p>`.
- `#chevron` slot. Default `ti-chevron-right`.
- `(reorder)` event. Emits `ISortableTreeReorderEvent` with `{ node, parent, oldIndex, newIndex }` after the splice. `parent` is `null` for top-level moves.
- `:beforeSelect?: (node: TNode) => boolean | Promise<boolean>`. Pre-selection guard. When supplied, every row click awaits the predicate; resolving to `false` cancels the selection AND the auto-expand-on-collapsed-row-click that normally rides on top of it, so a guard rejection leaves the previous selection and expansion fully intact. Re-clicking the already-selected row is treated as a no-op: the guard, auto-expand, and select emit are all skipped because no navigation is happening.
- `:isNodeDraggable?: (node: TNode) => boolean`. Per-node draggability predicate. Forwarded recursively from the parent to each child row and AND'd with the local "more than one sibling in this bucket" check. The control's existing single-sibling no-drag rule still applies; this prop layers an additional veto on top (used here to disable drag on placeholder rows with the sentinel idKey).

Block-specific decoration in `listPane.partial.obs`:

- Decorates `tree` with `iconCssClass` per node.
- Passes `:groupBy="groupByNodeType"` returning `"area"` or `"group"`.
- Passes `:actions` with `Add Area`, `Add Group`, etc., gated by `isVisible` predicates.
- Wires `@reorder` for tree reorder handling (server persistence still TODO).

CSS lives in `Rock.Frontend.Styles/src/styles/styles-v2/rock-components/_sortable-tree.scss` (registered in `core.scss`). Gallery at `Example/ControlGallery/sortableTreeGallery.partial.obs` (registered in `controlGallery.ts`).

### Drag-and-drop reorder

Sibling-only AND same-type-only enforcement is structural, not validation. Each parent's children render as one `.sortable-tree-list` per `groupBy` bucket (areas first by data-model invariant, then groups). Each list gets its own drag-service id. Areas and groups under the same parent are different services; lists at different parents are also different services. Top-level (under a check-in configuration) is always areas, so the top-level list uses a single service.

Implementation notes:

- Custom `IDragSourceOptions` per drag source (not `useDragReorder`) so the drop callback can splice the unified array correctly and emit the reorder event with the right indices.
- `startDrag` is scoped: the click's nearest `.sortable-tree-list` ancestor must be the drag source's source container. Without this, outer drag sources claim clicks on inner row handles and drag the parent.
- `dragBegin` / `dragEnd` toggle `.moving` on the source list for the dashed-border drop-zone.
- The floating clone the drag library appends to body is targeted via `body.sortable-tree-dragging > .sortable-tree-node` (real tree nodes always live inside a `.sortable-tree-list` ancestor). The rotated-3deg / 70%-opacity styling applies there.
- Reorder handle is `.sortable-tree-row-icon` (Rock's `reorder-handle` convention).
- The 5-level nesting cap is enforced at drop-time, plus the `+Area` action is hidden on level-5 areas.

Reference: [Rock.JavaScript.Obsidian.Blocks/src/Event/InteractiveExperiences/InteractiveExperienceDetail/actionsPanel.partial.obs](../Rock.JavaScript.Obsidian.Blocks/src/Event/InteractiveExperiences/InteractiveExperienceDetail/actionsPanel.partial.obs) (Daniel + Josh's flat-list pattern).

The legacy `CheckInTypeId` fallback was retained during initial conversion and has since been removed across `CheckInAreasAndGroups`, `CheckInScheduleBuilder`, and `CheckInConfigurationSettings` (along with the `PageParameters` cache, `_groupTypeKeyFromPageParameter` field, and `GroupTypePageParameterKey` property that the dual-resolution layer needed) now that the new routes own the page param.

## Accepted Behavior Differences from Legacy

A full audit of the legacy block surfaced several behavior deltas. The list below captures every difference that was reviewed and accepted as-is, with the rationale, so a future reviewer doesn't re-litigate them.

- **`PrintTo.Default` is normalized to `PrintTo.Kiosk` on save.** The new editor's radio (and the legacy `_ddlPrintTo` it replaces) only offer "Device Printer" (`Kiosk`) and "Location Printer" (`Location`); neither UI can represent `PrintTo.Default`. Both blocks therefore migrate any pre-existing `Default` value to `Kiosk` on first save. Confirmed parity, not a behavior change.
- **No tree expand-state restore across `GetTree` refetches.** Legacy `BuildRows( setValues: true )` re-seeds expansion from `ViewState["_expandedRows"]` (Guid list). The new block lets `<SortableTree>` manage local expand state and doesn't try to plumb it through `refetchTree()`. Accepted: legacy doesn't really have an expand/collapse concept in the modern sense (rows are always rendered expanded by `BuildCheckinAreaRow`'s `Expanded = true`), so there's no behavior to preserve. Auto-collapse is governed by the new `Disable Auto-Collapse` preference.
- **Placeholder auto-expand via SortableTree's ancestor-chain expansion** instead of an explicit `parentRow.Expanded = true` like legacy did before `SelectArea`. Accepted: the `selectPlaceholderForceExpand` flow nudges `selectedNodeKey` so the control's existing select-then-auto-expand logic kicks in and walks the ancestor chain.
- **Inherit-from change on the area editor relies on `LoadAttributes` (not the legacy "null then reload" sequence).** Legacy explicitly does `groupType.Attributes = null; groupType.LoadAttributes();` after setting `InheritedGroupTypeId` to force a re-resolve. New code orders the calls as `area.InheritedGroupTypeId = newValue; area.LoadAttributes( RockContext )` — the framework resolves the new chain when `LoadAttributes` runs against a fresh per-request entity. Accepted: behavior verified equivalent on a fresh per-request entity, which is the only context `SaveArea` runs in.
- **Add-Area tooltip wording.** Legacy row action reads "Add Sub Area"; new reads "Add Area" both at the top-level and on the row. Accepted: the redesign's icon (`ti-stack-2`) and context already make the sub-area meaning clear, and using the same label everywhere reads more consistently.
- **Empty placeholder name surfaces a validation error rather than auto-filling.** Legacy creates the GroupType / Group with `Name = "New Area"` / `"New Group"` immediately on Add click. New uses a placeholder bag pre-seeded with the same display name; if the admin clears the name field before saving, the new editor shows a required-field error. Accepted: the placeholder model already lets the admin Cancel out of a never-persisted row, so the "we won't auto-name silently" stance is the better UX.
- **Duplicate-location prevention is explicit, not silent.** Legacy `mdLocationPicker_SaveClick` silently no-ops when the picked location is already attached to either the Main or Overflow list. New `namedLocationsSection.partial.obs` `onPickerSave` surfaces an inline `pickerError` ("`{Name}` is already attached to this group.") and keeps the modal open. Both blocks prevent duplicates; the new UX is explicit. Verified locally.
- **5-level nesting cap on inline Add Area / Add Group.** Verified locally: at depth 5 both inline actions hide; at depth 4 both show and create a depth-5 placeholder; preexisting depth-6+ rows render but their inline adds stay hidden. The top-level "Add Area" button is never gated. Drop-time depth enforcement isn't implemented; in practice, drag-reorder is constrained to same-parent siblings so it can't push a row past the cap.
- **Per-variant filter rendering parity is `FieldType`-driven on both sides, not a block-level concern.** Both `<Rock:CheckinGroup>` (legacy, `Rock/Web/UI/Controls/Checkin Configuration Controls/CheckinGroup.cs:488`) and this block delegate the entire filter section to the same attribute-system dispatch: `Rock.Attribute.Helper.AddEditControls` on the WebForms side, `<AttributeValuesContainer>` on the Obsidian side. There are no hand-rolled `NumberBox` / `GradePicker` / `DataViewItemPicker` controls in the legacy control; every filter attribute resolves to the same `FieldType.Class` on both sides, so the input controls are identical by construction. The "By Age Range" decimal-vs-integer concern that originally raised this audit is a non-issue at the block layer: the `AgeRange` attribute is `Rock.Field.Types.DecimalRangeFieldType` (seeded as `FieldTypeId = 47` with value stored as `"min,max"` CSV) and Obsidian's `EditComponent` renders it as `<NumberRangeBox>` with `step="any"`, which accepts decimal keystrokes; the browser's spinner arrows step by 1 by UA default (cosmetic, not a value mismatch). Any apparent divergence in the filter section is a property of the Obsidian `FieldType` implementation, not of this block, and the fix (if any is warranted) belongs at the platform layer where it benefits every consumer.

## Open Questions

- **Worksurface panel-height overflow on pages with sibling chrome (parked; won't pursue unless reported).** Symptom: on the Full Width internal layout, the panel-height calc (`target = innerHeight - naturalTop` in `checkInAreasAndGroups.obs`) sizes the panel's bottom to the viewport bottom, leaving no room for the `.main-footer` and trailing page margins that sit below the block. Those push the page's real scroll container past its visible height by ~10-20px. Root cause (identified 2026-06-02): the calc measures against the window, but on this layout `documentElement` does not scroll. `#content-wrapper` does (`flex: 1; overflow: auto;` in `RockNextGen/Styles/theme.scss`), and the footer plus trailing margins live inside it, after the block, so that chrome is never subtracted. The two earlier fixes both derived overflow from `window` / `documentElement` (which reports zero overflow on this layout), which is why one froze the panel at natural height and the other applied no visible correction. Candidate fix if it ever needs doing: resolve the panel's nearest scrollable ancestor (`sc`) and compute `target = sc.clientHeight - offsetTopWithinSc - belowChrome`, where `belowChrome` is the summed height of in-flow following siblings walked from the panel up to `sc`. Measuring the chrome elements directly (not via `scrollHeight`) keeps it non-circular (no oscillation) and excludes flex-grow slack, so the panel still grows to fill when content is short as well as shrinks when it overflows. Decision: the overflow is cosmetic and this block is effectively the page's main content, so it is not worth the regression risk to chase now. Revisit only if reported.
- **Friendly type name constant.** Declined for now. The block doesn't expose a first-class model, so a `FRIENDLY_TYPE_NAME` constant alongside the `CheckInConfigurationSettings` pattern isn't a natural fit. Revisit only if a save-failure message ends up needing one.
- **"Requires Background Check" field provenance (resolved).** The Figma surfaced *Requires Background Check* as a top-level Group checkbox. It turned out to be a `Group` attribute defined on the group's own group type, not a hand-rolled entity property and not a check-in filter. Resolution: partition a group's resolved attribute schema into its inherited check-in filters and its own group-type attributes, and surface the two sets in separate UI sections. *Requires Background Check* and any other own attributes render in the new "Group Attributes" section; the inherited filters stay in "Check-in Filters." See the "Group attribute split" item under Done.
- **Backfilling filter attribute values on existing groups when an area's inherit-from changes.** Pre-existing in legacy; not introduced here. When admin flips Area A from None to "By Age Range" (or any filter type) and saves, groups already under A get the new filter schema on their next read but no rows are auto-created in `AttributeValue` for the new keys. The check-in v2 opportunity filters (`AgeRangeOpportunityFilter`, `GradeRangeOpportunityFilter`, `AbilityLevelOpportunityFilter`, etc.) treat a missing value as "filter not applied", so the practical effect is the new dimension simply doesn't filter the group until an admin sets values. Acceptable for now: legacy has the same behavior, the safe default is permissive (everyone matches) rather than restrictive (no one matches), and surfacing a "you have N groups with unset filter values" hint is a feature rather than a defect. Revisit if admins report confusion.
- **Area slicer contents vs the 5-level cap.** The Areas slicer lists every area descendant (flat). Scoping the tree to a *sub-area* renders that area at depth 1, and `listPane`'s `canHostNewChild` computes depth relative to the *rendered* root, so the 5-level cap resets: an admin can then nest past the global limit (a sub-area at absolute depth 3 allows 4 more levels = absolute depth 7). The cap is currently client-only and soft (no server enforcement in `SaveArea`; preexisting deeper hierarchies render), so the slicer is just one of several ways to exceed it. Options: (A) restrict the slicer to top-level areas (direct children of the configuration) so rendered depth always equals absolute depth — cheapest, closes the realistic UI bypass, loses sub-area focus, needs graceful fallback when a saved "Selected Area" preference points at a sub-area; (B) keep all areas and ship the scoped area's absolute depth so the client offsets its depth math — rejected leaning, since a multi-parent area's absolute depth is ambiguous; (C) keep all areas and enforce the cap server-side in `SaveArea` (reject when parent's shallowest depth + 1 > 5) — the only true hard-cap fix, makes slicer contents a pure UX choice. Decision pending: soft nudge → A; hard limit → C. Parked pending PO input.
- **Cache-usage pass — done, no change needed.** Walked every data-access point. The file is already cache-first for reads (`GroupTypeCache` / `GroupCache` / `NamedLocationCache` / `CampusCache` / `FieldTypeCache` for single-entity reads; `GroupLocationCache.GetMany` for attached-location field values). The remaining raw `Service.Queryable()` / `Service.Get()` calls are correctly *not* cached: write/edit paths need tracked entities (`Save* / Delete* / Reorder*`), aggregations can't be cached (`Max(Order)`, attendance `Any`), and the by-group / by-grouptype id lookups (`GetAttachedNamedLocations`, `FlushGroupCachesForAreaInheritedAttributes`, `BuildTree`) have no usable cache index (`GroupLocationCache` is indexed by location, not group; iterating `All()` would be worse). Only theoretical candidate is `GetAreaOptions` (uses `GroupTypeService.GetCheckinAreaDescendants` where the tree walk uses `GroupTypeCache`), left as-is to avoid reimplementing a canonical service method for a once-per-box-build path.
- **`TreeBuildContext` to shrink the tree-walk signatures.** `BuildAreaNode` / `BuildGroupNode` thread the same walk state through every recursive call (`groupRowsById`, `groupRowsByParentId`, `groupRowsByGroupTypeId`, `validAreaIds`, `hideInactiveGroups`, and the shared `visitedAreaIds` / `visitedGroupIds` sets); only the per-node `area` / `group` actually varies. Bundle the rest into a private `TreeBuildContext` so the signatures collapse to `BuildAreaNode( area, context )` and `BuildGroupNode( group, context )`. Matches the code-conventions "bundle behavior params into a POCO" guidance. Deferred; not changing now.

## Considered but Rejected

### Build for legacy parity first, then iterate to the Figma design

Rejected. The deliverable is the new design, not a one-for-one port. Targeting parity first is wasted work, since most of the legacy chrome does not survive the redesign. Use the legacy block as a behavior-and-data-flow reference instead.

### Manage campus picker in this block's bag and pass campus through every block-action call explicitly

Rejected. The framework already supplies a campus picker via `<ContextSlicer showCampus>` and routes the active campus through `RequestContext.GetContextEntity<Campus>()`. Decorating the C# class with `[ContextAware( typeof( Campus ) )]` lets actions read campus context without an explicit pass-through, keeps request bags slim, and matches the `CheckInScheduleBuilder` pattern.

### Single bag containing tree, area detail, and group detail

Rejected. Different concerns refresh at different times: the tree on filter change and structural mutation, area detail on Area selection, group detail on Group selection. Bundling them forces over-fetching on every interaction. The two-layer model (`InitializationBox` for once-and-done state, segmented bags returned by per-concern block actions) follows the Connection navigation blocks and keeps payloads scoped.

### Reserve viewport space for chrome below the panel via `belowPanel = scrollHeight - panel.bottom` in the height calc

Rejected. The term collapses to `innerHeight + currentPanelHeight - scrollHeight`, which on worksurface layouts (`scrollHeight === innerHeight`) reduces to `currentPanelHeight`. The calc then returned whatever the panel already was, locking it at natural content height. Observed in production: a worksurface page rendering at `scrollHeight: 762, innerHeight: 762, target: 1145` regardless of resize. Trade-off accepted: the calc no longer reserves viewport space for chrome below the panel, but in practice this block IS the main content. The remaining sibling-chrome overflow on worksurface pages is parked in Open Questions (won't pursue unless reported), where the identified root cause and a candidate fix are recorded.

### Vue type-form `defineProps<{...}>()` for the `<SortableTree>` control

Rejected. The type-form has known issues with generic components: Vue's compiler generates `PropType<T>` runtime types under the hood, and the type extraction misbehaves on access. The runtime form `defineProps({ ... type: X as PropType<...> ... })` keeps the control consistent with existing Rock controls and avoids those compiler edge cases.

### `useDragReorder` for the `<SortableTree>` per-bucket drag sources

Rejected for the recursive case. The block needs per-drag-source control over splice-and-emit because the unified `node.children` array is bucketed by `groupBy` at render time but stored as a single list. Custom `IDragSourceOptions` per drag source gives the drop callback the index math it needs (group offset for the second-bucket drag source) and lets the control emit a reorder event with the right payload. `useDragReorder` is still used at the top level, where there is only one bucket.

### `areas-and-groups-*` long CSS class prefix

Rejected. The shorter `ag-*` prefix (and `check-in-ag-*` for the outer panel container) is the final convention. The longer form added noise without disambiguating; `ag-` is unique enough inside this block's scope. The `<SortableTree>` control's classes were lifted into the generic `sortable-tree-*` namespace and are unaffected by this decision.

### Single graph-level `Save( payload )` action covering reorder, area save, and group save

Rejected. `CheckInScheduleBuilder`'s single `Save` works because it pairs with an explicit Save button at the bottom of the form. Areas-and-Groups has no Save button on the left pane: reorders persist instantly on drop, and the right-pane editors will own their own Save flow. A graph-level action would either force the client to ship the full tree on every drag (wasteful and lossy when concurrent edits land in unrelated branches) or require a partial-payload protocol that re-implements per-operation semantics. Per-operation actions (`ReorderArea`, `ReorderGroup`, eventually `SaveArea`, `SaveGroup`, etc.) keep each mutation scoped, let the server compute siblings authoritatively, and match the `useInvokeBlockAction` patterns already used elsewhere in Obsidian.

### Promote Location Selection Strategy to a discrete radio inside the conditional well

Rejected. LSS is just one GroupType attribute among potentially many that resolve onto an area through the inherit-from chain (qualified to specific check-in templates via the `EntityTypeQualifierColumn = 'Id'` pattern). Different inherit-from selections expose different attribute sets; LSS isn't actually static. Promoting it to a discrete control means hardcoding a field that may not apply to every inherit-from option, plus duplicating logic the AVC already handles for free. Generic `<AttributeValuesContainer>` inside the conditional well covers LSS along with everything else the inherited template defines, and adapts automatically when admins add or remove qualified attributes. The Figma's call-out of LSS is informative ("here's a representative attribute that should appear when an inherit-from is selected"), not prescriptive.

### Ship the per-area attribute schema on `AreaDetailBag.Attributes`

Rejected as redundant. `InitializationBox.InheritedAttributesByGuid` already carries the schema for every potential inherit-from option, keyed by setup-type Guid. The schema applicable to a specific area is just `box.InheritedAttributesByGuid[bag.InheritedGroupTypeGuid]` — fully derivable client-side, no per-bag duplication needed. The bag carries only `AttributeValues: Dictionary<string, string>` (the area's persisted values). Avoids two payload hazards: (1) sending the same schema repeatedly with every `GetAreaDetail` round-trip, and (2) drift between the bag's snapshot of the schema and the box's authoritative copy.

### Lazy-load attribute schemas on inherit-from dropdown change

Rejected in favor of shipping every schema up front on the `InitializationBox`. Lazy-loading would mean a block-action round-trip on every dropdown change, introducing a loading state in the conditional well as the user explores inherit-from options. Schemas for check-in filter group types are small (a handful of mostly enum-backed single-selects per template), so the upfront payload is modest. Better UX, simpler client state.
