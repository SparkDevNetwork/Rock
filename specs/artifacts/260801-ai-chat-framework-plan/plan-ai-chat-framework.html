01

Executive Summary

✅
Verdict: very feasible, and mostly a formalization job
Rock already ships a working streaming agent chat block (chatBot.obs + ChatBot.cs) with SSE token streaming end to end, an agent runtime with tools, skills, sessions, anchors, and auto-summarization, and a complete chat visual language in SCSS. What Rock does not have is what the Vercel AI SDK actually is: a typed stream protocol, a reusable client composable, and a composable component library. The plan below extracts and formalizes those three layers rather than building a chat product from scratch.

The Vercel AI SDK is really four products. Each has a natural Rock analog, and each maps to one phase of this plan:

  • AI SDK Core (streamText, tool calling, agents) → Rock's agent runtime, upgraded from Semantic Kernel to the Microsoft Agent Framework (1.0 GA April 2026, runs on net472).
  • UI Message Stream Protocol (typed parts: text-delta, tool-call, reasoning, data, finish) → a new typed SSE event contract replacing today's { message, tool, logs } blob.
  • AI SDK UI (useChat) → a useAgentChat() Obsidian composable in the Framework project.
  • AI Elements (Conversation, Message, PromptInput, Reasoning, Tool, Sources...) → a shared library of .obs controls under Framework/Controls/AI/.

Rock has one structural advantage Vercel does not: agent tools already return structured, typed results (PersonResult, GroupResult, FinancialTransactionResult, 24 entity result classes). That makes true generative UI (a person card, a giving summary chart, a group roster rendered inline in the conversation) a first-class capability instead of a JSON-parsing hack. This is the single biggest payoff of the whole effort.

⚠️
One structural constraint shapes everything
The concrete agent runtime (ChatAgent implementation, ChatAgentBuilder, all skill components) lives in Rock.AI.Agent, a separate assembly that is not in this repository (confirmed by InternalsVisibleTo in Rock/Properties/AssemblyInfo.cs:19 and the absence of any concrete implementations in-repo). Everything in this plan that touches the orchestration loop, including the Agent Framework migration, requires coordinated changes in that closed repo. The protocol, composable, and control library phases do not; they build against the abstract surface in Rock/AI/Agent/.

Target Architecture

Five layers, mirroring the AI SDK's separation. The protocol layer in the middle is the contract everything else composes against.

┌─────────────────────────────────────────────────────────────────┐ │ Obsidian AI Elements (Framework/Controls/AI/*.obs) │ │ Conversation · Message · Response · PromptInput · Tool · │ │ Reasoning · Sources · CodeBlock · Actions · EntityCard · ... │ ├─────────────────────────────────────────────────────────────────┤ │ useAgentChat() (Framework/Utility/agentChat.ts) │ │ messages · status · sendMessage · stop · regenerate · resume │ │ Transport: BlockActionSseTransport (default) │ │ RealTimeTopicTransport (durable runs) │ ├─────────────────────────────────────────────────────────────────┤ │ Agent UI Stream Protocol (Rock.ViewModels/AI/AgentStream/*) │ │ start · text-delta · reasoning-delta · tool-input · │ │ tool-output · entity-result · error · usage · finish │ ├─────────────────────────────────────────────────────────────────┤ │ Server orchestration (Rock.Blocks + Rock/AI/Agent) │ │ AgentChatStreamer: ChatAgent stream → protocol events │ │ Cancellation · message IDs · persistence of parts │ ├─────────────────────────────────────────────────────────────────┤ │ Agent runtime (Rock.AI.Agent assembly, external repo) │ │ today: Semantic Kernel 1.67 → target: MS Agent Framework 1.x │ │ Skills · Tools · MCP · sessions · auto-summarize · workflows │ └─────────────────────────────────────────────────────────────────┘

Two deliberate decisions:

  • The protocol is defined in Rock.ViewModels, not hand-written .d.ts, so the TypeScript types are code-generated and any block or plugin gets them for free. This also fixes gap #9.
  • An AgentChatStreamer adapter in Rock.Blocks (or Rock/AI/Agent) translates the runtime's stream into protocol events. This isolates the closed-assembly boundary: when Rock.AI.Agent later emits richer events natively (first-class tool results, reasoning), the adapter shrinks and nothing above it changes.

The Stream Protocol (the Linchpin)

Everything hangs off this contract. It is a direct adaptation of the AI SDK's UI Message Stream to Rock idioms: C# bags with a discriminator, camelCase JSON, SSE framing that the existing transport already handles.

Rock.ViewModels/AI/AgentStream/AgentStreamEventBag.cs (proposed shape, TS projection shown)
// Discriminated union, one SSE "data:" frame per event.
type AgentStreamEvent =
    | { type: "start"; messageIdKey: string; sessionIdKey: string }
    | { type: "text-delta"; delta: string }
    | { type: "reasoning-delta"; delta: string }                       // future: thinking models
    | { type: "tool-input-start"; toolCallId: string; toolName: string;
        preamble: string }                                             // "Looking up Ted Decker..."
    | { type: "tool-input-delta"; toolCallId: string; delta: string }
    | { type: "tool-output"; toolCallId: string; status: ToolStatus;
        resultType: string;                                            // "PersonResult", "SummaryResult", ...
        output: unknown }                                              // audience-filtered JSON
    | { type: "entity-result"; toolCallId: string;                     // generative UI hook
        entityTypeGuid: Guid; items: EntityResultBag[] }
    | { type: "data"; dataType: string; data: unknown }                // app-defined parts
    | { type: "usage"; inputTokens: number; outputTokens: number }
    | { type: "error"; message: string; isRetryable: boolean }
    | { type: "finish"; finishReason: "stop" | "toolCalls" | "cancelled" | "error" };

Server-side work in this phase:

  • Emit real SSE fields. Today only bare data: lines are written. Add event: names and monotonic id: values so Last-Event-ID resume becomes possible, and fix the technically malformed data: [DONE]\n terminator (single newline) in ServerSentEventsBlockActionResult.cs.
  • Thread cancellation. Pass the request's CancellationToken into GetStreamingChatMessageResponsesAsync() so a client disconnect or stop button actually stops the model call (gap #4, today it burns tokens to completion).
  • Surface message identity. Return IdKey for every persisted AIAgentSessionHistory row; persist tool-call parts (structured, in AdditionalSettingsJson or a new column) so a reloaded session renders identically to a live one.
  • Graduate the streaming result for plugins. Promote ServerSentEventsBlockActionResult<T> from internal to [RockInternal]-public, and add a REST v2 streaming result that reuses PushStreamContent + ScopedPushStreamContent (the DI-scope keeper in Rock.Rest/Handler/) for headless consumers.
  • Replace the log-regex tool detection. Move the parsing of tool activity server-side into AgentChatStreamer as an interim step; the durable fix (native tool-result events from the runtime) lands with the Agent Framework migration in Phase 4.

useAgentChat: the AI SDK UI Analog

One composable owns the client state machine, exactly like useChat. Blocks stop hand-rolling reader loops.

Rock.JavaScript.Obsidian/Framework/Utility/agentChat.ts (proposed API)
export function useAgentChat(options: AgentChatOptions): AgentChat;

interface AgentChatOptions {
    transport?: IAgentChatTransport;        // default: block-action SSE
    sessionIdKey?: string;                  // resume an existing session
    onToolCall?: (part: ToolCallPart) => void | Promise<unknown>;  // client-side tools
    onError?: (error: AgentChatError) => void;
    experimentalThrottleMs?: number;        // batch re-renders during fast streams
}

interface AgentChat {
    messages: Ref<AgentUiMessage[]>;        // parts-based, mirrors UIMessage
    status: Ref<"ready" | "submitted" | "streaming" | "error">;
    usage: Ref<UsageInfo | null>;
    sendMessage(text: string, files?: FileAttachment[]): Promise<void>;
    stop(): void;                           // aborts via ICancellationToken
    regenerate(messageIdKey?: string): Promise<void>;
    loadSession(sessionIdKey: string): Promise<void>;
    startNewSession(): Promise<void>;
    addAnchor(entityTypeName: string, entityId: number): Promise<void>;
}

A block then becomes declarative composition, the way an AI Elements app looks in React:

chatBot.obs after refactor (illustrative)
<AiConversation :messages="chat.messages.value" :status="chat.status.value">
    <template #message="{ message }">
        <AiMessage :message="message">
            <AiResponse v-for="part in textParts(message)" :markdown="part.text" />
            <AiTool v-for="part in toolParts(message)" :part="part">
                <AiEntityResult v-if="part.entityItems" :items="part.entityItems" />
            </AiTool>
            <AiActions :message="message" @copy="..." @regenerate="chat.regenerate" />
        </AiMessage>
    </template>
</AiConversation>

<AiPromptInput :status="chat.status.value"
               @submit="chat.sendMessage"
               @stop="chat.stop" />

The transport interface is small (start a stream, yield events, abort), which is what lets a RealTimeTopicTransport slot in later for durable runs without touching any component.

Backend Orchestration and the Agent Framework Move

You said you're happy to move from Semantic Kernel to the newer Microsoft agent platform. The timing is good: the Microsoft Agent Framework hit 1.0 (production GA) in April 2026, it is the convergence of Semantic Kernel and AutoGen, and critically its packages multi-target net472 / netstandard2.0, so it runs inside Rock's WebForms host. Rock already ships Microsoft.Extensions.AI 10.0.1, which is the abstraction layer MAF is built on.

Option A
Stay on Semantic Kernel 1.67
Keep the current runtime, build the protocol/UI layers on top, revisit later.
Pros
  • Zero runtime risk now
  • No closed-repo coordination
  • Phases 1–3 unaffected
Cons
  • SK agent APIs are in maintenance mode; MS steers new work to MAF
  • Tool events stay log-string based
  • No graph workflow story
Recommended
Option B
Migrate to Microsoft Agent Framework in Phase 4
Swap the internals of the Rock.AI.Agent assembly to MAF (ChatClientAgent over IChatClient), keeping Rock's abstract surface (ChatAgent, AgentTool, AgentToolResult) stable so blocks and skills don't churn.
Pros
  • 1.0 GA, runs on net472
  • Native streaming agent updates (typed tool events, no regex)
  • Graph workflows = the Vercel Workflows analog
  • Built on Microsoft.Extensions.AI already in RockWeb/Bin
  • OpenTelemetry hooks match Rock's observability
Cons
  • Requires the external Rock.AI.Agent repo
  • PromptExecutionSettings to ChatOptions semantic mapping
  • Token accounting parity must be re-verified

Durable orchestration (the Vercel Workflows analog)

Vercel's "use workflow" gives durable, resumable execution with per-step retry. Rock's equivalent composes from parts it already owns:

  • MAF graph workflows define multi-agent / multi-step orchestrations (sequential, concurrent, handoff) with checkpointing, inside the agent runtime.
  • A new AIAgentRun entity records a run's status, current step, checkpoint state, and results, giving admin visibility and resumability across app-pool recycles (Rock's version of "survives deploys").
  • Rock Jobs / transactions execute long-running runs off the request thread, with the existing retry conventions per step.
  • A new AgentRunTopic RealTime topic pushes progress and results to the owning person (Clients.Person(personId)), which is how a chat session shows "your background task finished" and how the RealTimeTopicTransport feeds the same UI components without an open HTTP stream.

This is deliberately staged last: it delivers the most new capability but depends on the protocol, the composable, and the runtime migration underneath it.

Issues We Will Face

IssueSeverityMitigation
Closed Rock.AI.Agent assembly. The orchestration loop, all skill components, and the provider registration live outside this repo. Native protocol events and the MAF migration cannot land without it. High Design the AgentChatStreamer adapter so Phases 1–3 need zero changes there; schedule Phase 4 with whoever owns that repo. Confirm ownership early (open question #1).
net472 ceiling. WebForms host, SignalR 2.x, no HTTP/2 server push, older TLS/socket behavior. MAF supports net472, but its ASP.NET Core hosting niceties (native SSE results, DI integration) don't apply; everything goes through PushStreamContent. High Rock has already solved the hard parts (ScopedPushStreamContent keeps DI scopes alive). Keep the protocol transport-agnostic so a future ASP.NET Core host swaps the writer, not the contract. The dual-target #if WEBFORMS aliasing convention in Rock.Rest must be followed in any new controller.
SSE through IIS and proxies. Response buffering, dynamic compression, and idle timeouts can stall or batch token streams; multi-minute agent runs can hit request timeouts. High Disable buffering/compression for text/event-stream, emit keep-alive comments, document reverse-proxy requirements. For anything long-running, hand off to the durable-run path (job + RealTime) instead of stretching HTTP.
XSS via streamed markdown. Model output rendered through v-html is attacker-influenceable (prompt injection through tool data), and today it is unsanitized. Medium DOMPurify in aiResponse.obs as a non-negotiable default; sanitize on every incremental render, not just the final text. Security review as part of Phase 3 exit.
Protocol versioning and back-compat. Once plugins consume the stream and the composable, the event contract is a public API under Rock's strict compatibility rules. Medium Ship behind [RockInternal] for one release cycle, include a protocol version in the start event, additive-only evolution after graduation.
SK to MAF semantic drift. PromptExecutionSettings to ChatOptions, keyed IChatCompletionService to IChatClient, token usage metrics, and tool-choice behavior all shift subtly. Medium Golden-transcript tests: run recorded conversations against both runtimes and diff messages, tool calls, and token counts before cutover. The abstract surface means blocks never see the swap.
Web farm behavior. SSE streams pin to one server (fine), but RealTime push for durable runs needs the Azure SignalR backplane story validated, and session state must stay DB-backed (it already is). Medium Rock.csproj already references Microsoft.Azure.SignalR.AspNet; include a farm test pass in Phase 4.
Session reload fidelity. Tool messages are persisted but filtered out of history today, and parts aren't stored, so a reloaded session would lose tool cards. Medium Phase 1 persists parts alongside text; the history query returns them keyed by message IdKey.
Rock Store packaging. Any new binary (MAF packages, DOMPurify is JS so exempt) must be added to the PackageInstall.cs bin blacklist or plugin installs can clobber it. Low Checklist item in the Phase 4 PR template.
Naming collision. "Chat" already means the Stream.io person-to-person feature (ChatMessage, ChatChannel, ChatController). Low Prefix everything Agent* / AiAgent* (AgentStreamEvent, useAgentChat, AgentRunTopic), matching the existing AIAgent* entities.

Open Questions

To resolve before Phase 1 ends
1
Who owns the Rock.AI.Agent repo, and can Phase 4 get on its roadmap?
The MAF migration and native tool-event emission both land there. If it's Spark core team territory, this plan's Phase 4 becomes a joint effort; if Triumph has commit access, it's ours to schedule.
2
Is the plugin surface a v1 goal?
Graduating the streaming result, the protocol bags, and the composable to plugin-visible API is cheap in code but expensive in compatibility promises. Recommendation: build it public-shaped, ship it [RockInternal], graduate after one release.
3
Which surfaces beyond the Chat Bot block are in scope?
A person-profile copilot panel, an admin-bar "ask Rock" launcher, and block-embedded assistants all become one-day builds once the library exists, but knowing the first target shapes wave 2 control priorities (entity results vs. artifacts).
4
Do we need multi-provider model routing at launch?
ModelServiceRole has a single Default value today. MAF's IChatClient makes per-role routing (fast model for summarize, strong model for chat) straightforward; deciding now avoids a schema change later.
5
How aggressive should the docked-mode rework be?
The current docked bootstrap serializes outerHTML into sessionStorage with a MutationObserver, which is fragile. Rebuilding it on the composable + RealTime session sync is cleaner but adds roughly a week to Phase 3.
